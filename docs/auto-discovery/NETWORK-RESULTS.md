# 校园 Wi-Fi 第一轮网络实测

记录日期：2026-10-13。结论：当前校园位置电脑到手机的两类 UDP 广播均有实际接收证据，但存在明显丢包；手机到电脑的现有 WebSocket 握手通过。可以继续设计周期公告、重试与去重，不具备宣称稳定上线的证据。

## 条件与方法

- 一台 Windows 电脑、一台小米 10 / Android 13，双方无线连接当前校园 Wi-Fi。按电脑当前 IPv4/子网掩码计算定向广播地址；本机实际地址留在 START-HERE.md，不作为协议常量。
- 手机通过无线 ADB 安装独立 `com.skycommand.networkprobe` 测试 App，前台监听 UDP 39081，保持屏幕亮起，无 DJI 依赖；生产 Relay 未替换。
- 电脑使用 `scripts/send-network-probe.ps1` 绑定实际 WLAN IPv4。每类目标三轮，每轮 20 包、间隔 1 秒，以 UUID 区分组，按手机实际收到的唯一序号计数。
- 手机 App 直连正在运行的 Sky Command 的 8080/relay，二进制 UTF-8 JSON 发送 hello，接收合法 paired，随后以 code=1000 关闭测试会话；没有发送业务命令。
- 测试期间没有修改 Windows 防火墙规则，没有重连 Wi-Fi 或移动到其他校园位置。测试结束后已停止独立测试 App，安装包仍留在本机。

## 最终结果

| 目标类型 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 合计 |
| --- | --- | --- | --- | --- |
| 手机单播 | 20/20 | 20/20 | 20/20 | 60/60 |
| 当前子网定向广播 | 8/20 | 11/20 | 15/20 | 34/60 |
| 有限广播 255.255.255.255 | 12/20 | 14/20 | 10/20 | 36/60 |

分子为收到的唯一序号数，分母为发送数量。不能仅按“sequence=20”推断全部送达，也不能因某次短日志截取为空就记为零接收。第一轮定向广播的早期截取漏掉接收记录；最终较完整日志中存在该 testId 的 8 个唯一序号，以上以最终汇总为准。

WebSocket 证据：WS_OPEN http=101 → HELLO_SENT binary protocolVersion=1 → WS_PAIRED → WS_RESULT paired=true → WS_CLOSED code=1000。初版探针误用了文本帧，被现有协议拒绝；已修正并重新编译安装。这个开发错误不计作网络失败，也没有因此修改正式协议。

原始发送记录、接收日志和最终汇总位于本机被忽略的 `Sky-Command/tmp-network-probe/`，包含现场地址，不进入源码提交。接收日志与发送端均记录时间，但两端时钟未校准，本次不报告精确首包延迟。

## 对最小方案的影响

两种广播都有到达证据，不能认定校园网完全屏蔽广播，也无法仅凭这些计数判断丢包原因。当前样本不支持认定有限广播始终优于定向广播；候选实现可考虑绑定实际网卡并发送两类短公告，手机去重，具体周期和端口仍待确定。

单次公告有丢失风险，应持续公告和等待发现，成功连接后忽略重复公告，避免反复建连。只把 hello/paired 成功当成已连接；发现公告不是认证凭据。当前数据不是独立丢包模型，不能用累计比例推导等待若干秒必然连接的保证。

- 跨 AP、跨 VLAN、其他校园位置和其他网络。
- 两台及更多手机、实际无人机/遥控器连接、DJI 注册、图传。
- 正式 Relay 的发现监听接线、后台/锁屏和省电限制。

下一步先确定上述产品/接入边界，并补充 Wi-Fi 重连和多手机场景；之后更新两端契约、实施最小方案。此测试证明当前条件下的网络路径，不能替代自动发现功能验收。

实测后用户已确认：保持当前电脑连接、未连接且多个候选时显示冲突并等待；第一版沿用现有未认证 v1 做受控联调；首轮验收 2 台手机/2 架无人机；后台/锁屏/划掉任务卡片后继续运行；保留隐藏调试入口；连接耗时目标 15 秒。正式 Relay 尚未实现上述功能，系统通知、首次授权和进程恢复边界见 TASK.md。
