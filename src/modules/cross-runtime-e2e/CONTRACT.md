# 跨运行时端到端验证模块契约

状态：已实现，软件边界可自动验收；所属：验证模块，不属于产品运行时。

## 1. 唯一职责

`cross-runtime-e2e` 的唯一职责是：通过**真实 TCP/WebSocket** 验证 Sky Command 与 MSDK Relay 的全部当前生产可达模块能否完成受控业务闭环，并把观察到的最终状态、覆盖矩阵与失败证据输出为确定性验证报告。

它不是生产功能。任何 Electron、桌面业务、Android 业务、DJI 适配器或 UI 都不得依赖它；它不向操作者开放命令，不写入产品设置，不连接外网，也不替代 DJI 真机验收。

删除本模块后，产品功能仍可运行；只会失去跨进程端到端验证能力。所有跨语言进程编排、等待、诊断收集、临时资源清理、覆盖矩阵和仿真设备控制必须集中在本模块，不能散落到各业务模块的单元测试中。

## 2. 对外接口

```text
npm run test:cross-runtime-e2e
  -> CrossRuntimeVerificationReport
  -> cross-runtime-verification-report.json
```

该命令是本模块唯一对外接口。调用者不需要知道端口、进程、WebSocket、OkHttp、DJI 替身、测试数据、延时或帧编码细节。

通过时报告至少包含：场景名称、通过状态、§4.1 的模块覆盖矩阵及 §4.5 的情形矩阵。报告固定写入项目根目录 `cross-runtime-verification-report.json`；任何必需项失败或未覆盖时命令必须以失败退出码结束。失败时报告至少包含：场景名称、失败步骤、最近一次安全桌面快照、最近一次安全手机快照、最近观察事件以及子进程退出状态。报告不得包含完整 WebSocket 地址、密钥、用户文件内容、真实设备标识、原始帧、绝对路径或堆栈。

## 3. 运行架构

### 3.1 正式桌面端宿主

内部 `desktop-test-host` 进程必须创建并使用以下正式实现：

```text
NodeWebSocketRelayTransport
-> RelayLink
-> RelayOperationsAdapter
-> DesktopSettings / RouteLibrary / GeoMap / DeviceConsole
-> MissionControl / FlightControl / LiveStreamControl / MediaPipeline
-> DesktopRuntime / NodeRuntime
```

它监听回环地址的随机端口，绝不监听局域网地址。它必须从正式 `desktop-settings` 读取测试专用的回环配置；使用 `route-library` 导入运行时生成的最小合格 KMZ，使用 `geo-map` 的公开预览模型和渲染适配器接口验证航线可视化输入，使用 `media-pipeline` 与 `live-stream-control` 驱动图传控制链。它通过私有标准输入/输出控制通道接收测试动作：等待设备、读取安全快照、传输固定测试 KMZ、下发受限命令、等待状态、关闭。控制通道不是产品 API，不能被生产组合根或 UI 导入。

### 3.2 正式手机端宿主

内部 Kotlin/JVM `relay-test-harness` 必须创建并使用以下正式实现：

```text
OkHttpTransportConnector
-> RelayGateway
-> CommandDispatcher
-> WaylineMission / FlightControl / DeviceSettings / Telemetry
```

它必须使用正式协议编码器、解码器、会话代次、命令分发和出站发布器；不得通过内存 transport、直接函数调用或手写 JSON 绕过网络边界。

`MobileRelayGraph` 本身依赖 Android 与真实 DJI 端口，不能在普通 JVM 中诚实运行。因此本模块验证其所装配的正式一级模块和注册命令，不声称已经验证 Android Activity、权限、USB 或 DJI SDK 初始化。

### 3.3 仿真 DJI 适配器

唯一允许替换的外部接缝是 DJI/Android 端口、受控时钟和测试文件存储。`simulation-dji-adapter` 必须：

- 对上传、启动、暂停、恢复、停止、起飞、降落、返航、相机与图传读写分别配置接受、拒绝、超时或重复回调；
- 只通过正式手机模块的已公开回调入口发送航线阶段与遥测事实；
- 返回完整、封闭且可验证的设置快照；
- 模拟连接失效、重连、旧会话回调及迟到 DJI 回调；
- 不构造 Relay 帧、不读取或修改桌面状态、不复制协议逻辑。

## 4. 必须验证的业务闭环与覆盖矩阵

### 4.1 当前生产可达模块覆盖矩阵

端到端命令通过时，下表每项都必须有至少一个场景实际跨越其公开接口；仅在源代码中被导入、由替身重写、或只通过单元测试均不算覆盖。

| 端 | 一级模块 | 端到端验证责任 |
| --- | --- | --- |
| 桌面 | `desktop-settings` | 测试专用回环 WebSocket、地图和媒体配置经过正式读取、校验与注入。 |
| 桌面 | `relay-link` | 真实监听、握手、遥测、命令结果、KMZ 分块、阶段帧、会话替换与关闭。 |
| 桌面 | `device-console` | 设备链路、能力门禁、配对、相机和图传设置结果在桌面快照中准确表达。 |
| 桌面 | `route-library` | 最小合格 KMZ 经正式导入、资格判定、目录与预览负载进入任务链。 |
| 桌面 | `geo-map` | 正式航线预览模型被地图适配器接收，定位和图元输入与已导入航线一致。 |
| 桌面 | `mission-control` | 暂存、上传、启动、阶段、终态、失效和断线不会混淆。 |
| 桌面 | `flight-control` | 显式确认、启动前检查、命令结果与遥测事实不混淆。 |
| 桌面 | `live-stream-control` | 按设备生成 RTMP 目标并准确下发开始/停止命令。 |
| 桌面 | `media-pipeline` | 接收端点、进程编排、HLS 服务和播放就绪状态经公开接口协同；使用受控本地媒体进程替身，不声称已验证真实视频像素。 |
| 桌面 | `app-shell` | 当前只验证其公开生命周期、路径、窗口与 IPC 规则的无 Electron 替身实现；真正 Electron 装配尚未存在，不能标为产品界面已验证。 |
| 手机 | `relay-settings` | 测试专用电脑地址与匿名测试设备身份经正式设置接口提供给网关。 |
| 手机 | `relay-gateway` | 正式 OkHttp 连接、握手、帧收发、命令分发、结果发布和会话代次。 |
| 手机 | `device-connection` | 仿真 DJI 设备事实、共享操作串行、失效和回调隔离。 |
| 手机 | `telemetry` | 正式状态源组装、去重、主动读取和持续发布。 |
| 手机 | `wayline-mission` | 暂存、上传、启动、暂停、恢复、停止、阶段与终态。 |
| 手机 | `live-stream` | RTMP 控制请求、状态和结果；不产生真实视频。 |
| 手机 | `flight-control` | 三个高风险命令的确认、串行、超时、取消和结果。 |
| 手机 | `device-settings` | 完整快照回读和结构化结果。 |
| 手机 | `runtime-diagnostics` | 断线、拒绝和启动失败产生脱敏且可被桌面读取的诊断记录。 |
| 手机 | `app-runtime` | 当前只验证 Bootstrap 的有序启停与模块失效通知；Android Activity、权限、USB 与系统服务属于真机/模拟器验收。 |

`route-planning` 是桌面端已明确未装配的历史研究代码；`wpmz-generator` 是手机端已从 Gradle 工程、生产依赖和命令目录移除的历史源码。两者必须在报告中明确列为“非生产可达，未纳入端到端验收”，不得被遗漏或冒充通过。

### 4.2 航线

1. 中继完成 `hello / paired` 后，桌面发现设备并收到满足启动前检查的遥测。
2. 桌面传输固定的最小合格 KMZ；手机暂存成功后，桌面仅进入 `staged`。
3. 桌面下发 `wayline.upload`；仅手机确认 DJI 上传成功后进入 `uploaded`。
4. 桌面下发 `wayline.start`；手机确认 DJI 接受启动请求后，桌面必须保持 `starting`。
5. 仿真 DJI 经手机正式航线回调发布 `ROUTE_EXECUTION_STARTED`；桌面才可进入 `running`。
6. 仿真 DJI 发布 `FINISHED` 或 `FAILED`；桌面分别进入 `completed` 或 `failed`。

不得把文件已暂存、上传请求已发送、手机收到命令、DJI 接受启动请求、`RETURN_TO_START_POINT` 或自由文本当成航线已完成。

### 4.3 飞控、设置和图传控制

- `flight.takeoff`、`flight.land`、`flight.return-home` 缺少 `{ confirm: true }` 必须被拒绝；带确认时，命令结果只代表 DJI 调用终态，飞行事实仍由遥测表达。
- 四个 `device.settings.*` 命令必须将与请求域匹配的完整快照置于 `command-result.result`；缺失、跨域、额外替代字段、无效枚举或非法数值不得更新桌面设置状态。
- `live-stream.start|stop` 必须到达手机端并产生对应命令结果。本模块仅验证控制链，绝不声称 RTMP 接收、转码或播放成功。

### 4.4 失效与隔离

以下每类场景都必须有独立端到端测试：KMZ 摘要不匹配、命令超时、DJI 拒绝、桌面停止、手机断线重连、旧会话命令结果、重复 DJI 回调、迟到航线阶段、任务文件名不匹配、结构化设置结果无效。

每个场景必须断言：当前任务不被旧事实污染；未确认动作不显示成功；没有悬挂命令；进程仍可关闭；下一场景可从干净状态开始。

### 4.5 全面情形覆盖规则

“覆盖所有可能情况”在本契约中有严格、可验证的含义：对接口定义的**有限状态、有限枚举、状态转换和输入等价类必须穷尽**；对无限值域、无限长度序列和外部真实环境必须用边界覆盖、生成式序列和故障注入逼近，且不得把这部分称为数学上的全穷尽。

端到端验证必须同时满足以下矩阵：

| 情形类别 | 必须覆盖的内容 |
| --- | --- |
| 状态转换 | 每个已启用模块的每个封闭状态、每条合法转换、每条非法转换、每个终态后的重复请求、停止后的迟到回调。 |
| 输入等价类 | 每个命令的空值、缺字段、额外字段、类型错配、最小值、最大值、刚越界值、Unicode、控制字符、重复 ID、非法文件名、非法摘要和畸形结构化结果。 |
| 网络与会话 | 初次连接、握手前断开、握手超时、会话替换、发送失败、读写并发、旧代次帧、重连、桌面先停、手机先停及重复关闭。 |
| DJI 结果 | 每项可调用操作的接受、同步拒绝、异步拒绝、超时、取消、重复成功、成功后失败、失败后成功及迟到回调。 |
| 航线时序 | 暂存、上传、启动、阶段、暂停、恢复、停止、终态的全部合法排列；每个非法排列、任务代际不匹配、设备代际不匹配、序号倒退和重复序号。 |
| 多设备隔离 | 至少两台中继同时在线、不同航线并行、其中一台断线/失败/重连时，另一台的任务、设置、图传和遥测保持不变。 |
| 资源与恢复 | 子进程、端口、临时文件、订阅、定时器和 WebSocket 在成功、失败、超时及强制停止后的释放；同一完整套件连续运行至少两次结果一致。 |
| 协议与安全 | 每类有效帧和所有已声明的非法帧类别、文本帧、截断帧、超限帧、未知帧、错误诊断脱敏及不泄露原始数据。 |

无限情况的验证必须使用有固定种子、可重复的模型驱动生成式测试：随机生成有界长度的命令、网络、回调和时间推进序列；每一步都以公开状态机和快照不变量为预言机。失败时必须输出种子和最小化后的动作序列，确保可稳定复现。生成式测试不允许绕过真实 WebSocket、两端正式协议或正式业务模块。

每个 DJI 外部接缝都必须有“正常、拒绝、抛出、超时、重复、迟到”六类故障注入；缺少其中任何一种，报告必须将该接缝标为未完全覆盖，而不能报告整体通过。报告必须分别列出以下 30 项，不允许退化为聚合的六项：

| 接缝 | 必需报告项 |
| --- | --- |
| 飞控 | `dji-flight-normal/reject/throw/timeout/duplicate/late` |
| 航线上传 | `dji-mission-upload-normal/reject/throw/timeout/duplicate/late` |
| 航线控制 | `dji-mission-control-normal/reject/throw/timeout/duplicate/late` |
| 设备设置 | `dji-settings-normal/reject/throw/timeout/duplicate/late` |
| 图传控制 | `dji-stream-normal/reject/throw/timeout/duplicate/late` |

生成式动作序列使用固定种子 `20260813`。同一代码版本、工具链和运行环境下，动作顺序与失败位置必须可重复。

## 5. 资源、时间与安全

- 每个场景使用独立随机端口、临时目录和进程代次；结束时必须关闭 WebSocket、停止子进程并删除本场景临时资源。
- 所有异步等待必须有明确、有限的截止时间；等待失败时输出 §2 的受限证据，不能无限挂起。
- 固定测试 KMZ 必须由测试在运行时生成，不得读取用户航线、密钥、真实设备标识或外网资源。
- 测试运行时不得向局域网广播、修改防火墙、安装 APK、调用 DJI 服务或执行飞行命令。
- `MediaPipeline` 只使用受控本地进程端口验证接收、转码、HLS 和播放编排；本模块不检查真实 RTMP 视频像素。

## 6. 验收边界

本模块通过只能证明：§4.1 所列的每个当前生产可达模块都已在至少一条真实跨进程业务路径中协同运行，且各路径已满足对应断言；它不能证明未实现的 Electron 产品装配或外部硬件/媒体环境。

以下仍必须通过真机验收，且不得由本模块伪装为已通过：Android 权限和 USB、MSDK 注册、RC-N2 与飞机链路、目标机型的 KMZ/WPML 上传及执行、DJI 回调顺序、相机/AirLink 键、RTMP 实际推流、接收、转码与播放。

## 7. 交付标准

实现前，`desktop-test-host`、`relay-test-harness` 和 `simulation-dji-adapter` 各自必须在自身目录新增中文 `CONTRACT.md`，并只说明各自的单一职责。根模块的实现必须先有一条失败的正常航线闭环测试，再实现最小编排；其后每增加一类失效场景，必须先增加对应失败测试。

最终必须提供一个独立可重复运行的命令，并同时通过 Sky Command 常规检查、MSDK Relay 的 `check`、Debug APK 构建和端到端验证命令。端到端报告必须逐项列出 §4.1 模块和 §4.5 情形矩阵的覆盖状态；任何一项失败或未覆盖都不能宣称完整跨端链路已验证。
